# 探索收尾与选点性能分析

> 归档说明：本文记录 2026-09-12 的问题分析，部分门禁、收尾和连续选点问题已经在后续实现中修复。
>
> 当前实现参考：`d7be6c6`（2026-09-24），请勿将本文的“当前问题”直接视作现状。

## 1. 结论

当前“地图留下小块未知区域”和“每次换点机器人都会停下来”不是同一个问题，但都能从现有代码路径解释：

- 收尾不干净的主要风险在 **frontier 检测、候选生成和硬门禁**，不是单纯分数不够好。当前链路会永久忽略单格 frontier、地图边缘 frontier，并可能把暂时生成不了候选的 cluster 提前加入黑名单。
- 当前完成条件是 **本轮未检测到 frontier 就算完成**。它无法区分“真的没有可探索区域”和“frontier 被边界、安全、尺寸规则过滤掉了”，存在假完成风险。
- 停车选点是 **控制流串行化** 导致的。机器人到达一个目标以后，系统先重新计算候选，再逐个调用 Nav2 规划器检查最多 16 个候选，全部检查结束才下发下一导航目标。这期间 Nav2 没有活动目标，因此机器人自然停住。
- 现阶段不应直接上 ML/RL。排序器只能给已经存活的候选排序，无法挽救在 Detector/Pruner 阶段被删掉的小区域。

推荐路线：先补可观测性，再做“两阶段 frontier + cleanup”，同时把选点改成“导航期间预计算、到点前确认、到点后快速续接”。之后再把候选生成升级为基于传感器可见未知面积的 Next-Best-View（NBV）。

## 2. 当前主链路

```text
地图 / costmap
  -> FrontierDetector
  -> FrontierPruner（尺寸、未知率、安全、距离、黑名单）
  -> RuleBasedFrontierRanker
  -> GetFrontierCandidates service
  -> BT 逐个 CheckGoalFeasibility
  -> 选出全量候选中的最优可行点
  -> NavigateToFrontier
  -> 导航结束后重新加载 BT，再开始下一轮
```

## 3. 已由代码确认的问题

### 3.1 小区域被遗漏

1. Detector 只扫描 `1..rows-2` 和 `1..cols-2`，地图最外圈不会成为 frontier。
2. `is_frontier_cell_safe()` 把邻域越界也视为不安全；当安全半径为 1 时，靠近地图边界的候选会被拒绝。
3. `min_frontier_cluster_size: 2` 会永久跳过单格 cluster。“延后小 cluster”发生在此之后，无法恢复已经被最小尺寸门禁删除的 cluster。
4. 候选周围 2 格范围内未知占比必须不超过 0.25。frontier 天然位于已知/未知交界处，这个门禁在收尾阶段可能比正常阶段更容易删除有价值候选。
5. 候选生成主要依赖 cluster 中心、最近 frontier 点、朝机器人方向退让，以及固定 0.35/0.55 m 环采样。它验证“能不能站”，却没有计算站在那里后传感器能否真正看到剩余未知区域。
6. 多个 cluster 经过向机器人方向内缩后可能落到同一网格；全局 `emitted_goals` 去重后，一部分 cluster 会失去候选。
7. 某个 cluster 本轮没有生成候选时，失败次数会立即增加；达到阈值后进入 cluster 黑名单，即使它只是受地图更新、costmap 延迟或暂时姿态影响。
8. cluster 身份直接使用会随地图变化而漂移的 centroid，不是稳定的空间区域标识。
9. `max_frontier_failures` 虽已配置和记录，但当前没有参与恢复或终止判断。

### 3.2 完成判定可能过早

`FrontierStrategyPolicy` 在 `clusters.empty()` 时直接返回 `COMPLETED`。这里的空集合是“经过当前 Detector 定义和安全检查后为空”，不等价于“所有可达未知区域都已探索”。

因此完成判定至少要区分：

- 没有原始 frontier；
- 有原始 frontier，但被尺寸门禁删除；
- 有 cluster，但没有安全候选；
- 有候选，但 Nav2 认为不可达；
- 剩余未知区域属于地图外边界、障碍封闭区或真正不可达区。

### 3.3 评分并非首要根因，但存在不一致

- 距离和 cluster 大小按“本轮候选集合”做 min-max 归一化，同一个点在不同轮次的分数不稳定。
- 信息增益把未知率 0.35 当作有用密度上限，但候选门禁先要求未知率不超过 0.25，较高潜在收益候选在评分前已被删除。
- 同分时排序器反而偏向更远候选，与距离得分偏向近点的语义不一致。
- 目前没有区域级滞回和目标粘性，地图稍有变化就可能切换局部最优点。

### 3.4 选点期间停车

当前 BT 是严格串行的：

```text
ComputeFrontierCandidates
  -> SelectFeasibleFrontier
       -> candidate 0 调 ComputePathToPose
       -> candidate 1 调 ComputePathToPose
       -> ...
       -> 最多 candidate 15
  -> NavigateToFrontier
```

每个可行性检查内部会等待 Nav2 `ComputePathToPose` 的 goal response 和 result，单次配置超时 2 秒；遇到可恢复错误还会按候选重试，并等待 2 秒。系统检查完所有候选后才选择最优项。在此之前没有导航目标，所以停车是架构行为，不是 CPU 算分慢。

导航成功后，编排器还会重新创建整棵 BT，再启动下一轮候选计算。当前没有：

- 导航期间预取下一候选；
- 可行性结果缓存；
- Top-K 早停；
- 候选并行检查；
- 行驶中的目标重评估和有条件替换。

## 4. 需要运行数据确认的部分

静态代码只能确认存在风险，不能证明每个残留区域具体死在哪一道门禁。实施前应复现一次并记录：

- 每轮原始 frontier cell 数、cluster 数；
- 按原因统计的拒绝数量：边界、尺寸、距离、未知率、footprint、重复、goal 黑名单、cluster 黑名单、不可达、路径不安全；
- 每个剩余未知连通域是否拥有 frontier、候选和可达路径；
- Detector、Pruner、Ranker、每次 `ComputePathToPose`、总选点阶段耗时；
- 从前一导航成功到下一导航 goal accepted 的空窗时间；
- `/map`、global costmap、TF、frontier markers、候选及规划路径的 rosbag。

验收前不要只看总 `unknown_ratio`，还要看“可达空间内的剩余未知连通域”。

## 5. 方案比较

| 方案 | 收尾能力 | 连续性 | 成本 | 判断 |
|---|---:|---:|---:|---|
| 只调小 cluster/未知率参数 | 小幅改善 | 不改善 | 低 | 只能用于验证，不能作为最终修复 |
| 两阶段 frontier：正常模式 + cleanup 模式 | 明显改善 | 可同时优化 | 中 | 当前最适合 |
| 基于传感器可见性的 NBV 候选生成 | 强 | 可在线计算 | 中高 | 第二阶段推荐 |
| 完整 Active SLAM（地图与位姿联合不确定性） | 强，兼顾地图质量 | 取决于实现 | 高 | 暂不需要 |
| ML/RL 排序 | 依赖候选质量 | 可改善路径效率 | 高 | 等确定性链路稳定后再做 |

## 6. 推荐设计

### 6.1 正常模式与 cleanup 模式

正常模式继续使用保守门禁，优先快速覆盖大区域。满足以下任一条件后进入 cleanup：

- 一段时间内 explored ratio 不再明显增长；
- 只剩小 cluster；
- 候选连续多轮为空，但仍存在可达空间附近的未知连通域。

cleanup 模式应：

- 接受单格/小型 frontier，但仍保留 footprint 和路径安全硬约束；
- 正确处理地图边界，而不是把邻域越界等同于障碍；
- 自适应放宽未知率门禁；
- 围绕剩余未知连通域生成“观测位姿”，而不是简单使用 frontier centroid；
- 用传感器视场、量程和遮挡估计该位姿能看到多少未知单元；
- 对不可达区域保留结构化原因，不因三次瞬时失败永久拉黑。

完成条件建议改成：连续 N 个稳定地图版本中均不存在“可达且信息增益超过阈值的观测位姿”，同时剩余未知域都已被分类为地图外、障碍封闭、低收益噪声或不可达。`explored_ratio` 仍只是进度指标。

### 6.2 边跑边选

“边跑边选”应表示计算重叠，而不是同时向 Nav2 发多个活动目标：

1. 当前目标导航期间，后台根据新地图持续生成并排序下一批候选。
2. 只对 Top-K（建议先从 3～5 个验证）执行规划可行性检查；有足够高效用的可行点即可早停，不必固定检查 16 个。
3. 缓存路径长度和可行性，缓存键至少包含地图/costmap 版本、机器人起始区域和目标区域。
4. 接近当前目标时，用最新位姿和 costmap 对预取目标做一次快速确认。
5. 当前目标结束后立即下发已确认的下一目标，缩短零速度空窗。
6. 只有新目标效用显著更高且当前目标已保持足够时间时，才允许行驶中替换，避免目标抖动。

Nav2 自己的默认导航树已经使用 `PipelineSequence` 让路径规划与控制并行，并周期性重规划；探索层可以采用同类思想，但要把“路径重规划”和“探索目标替换”分开，后者必须带滞回。

## 7. 实施顺序与验收门槛

### P0：观测与基线

- 增加逐门禁拒绝计数、各阶段耗时和导航空窗时间。
- 固定 3 类地图：开阔区、窄门/凹槽、小未知孤岛。
- 基线指标：覆盖率、剩余可达未知域数、总路程、总时间、平均/最大停车选点时间、目标切换次数。

### P1：修正确性

- 修边界 frontier、单格 cluster 和假完成判定。
- 将“候选生成失败”与“导航实际失败”分开计数。
- 黑名单改成有 TTL/地图版本，并使用空间区域而非精确单元格身份。
- 增加 cleanup 模式。

### P2：降低停车时间

- Top-K + 早停；再评估是否需要有限并发。
- 加可行性缓存。
- 导航期间预计算下一候选，到点前复核。

### P3：升级候选质量

- 候选由“frontier 点”升级为“传感器观测位姿”。
- 效用统一为：预计可见未知量 - 路径成本 - 风险 - 切换惩罚。

建议验收目标先定为：

- 不再出现“仍有可达未知域但状态为 COMPLETED”；
- 小区域场景的可达未知域清零率显著提高；
- 相邻导航目标之间的 P95 停车选点时间小于 0.5～1.0 秒（最终阈值按 Ubuntu 实机基线确定）；
- 不因边跑边选出现频繁 cancel/re-goal 或明显路径振荡。

## 9. 当前决策

结论为 **CONDITIONAL_GO**：可以继续优化，优先采用“两阶段 frontier + cleanup + 导航期间预计算”的渐进方案。进入实现前先完成 P0 观测，否则无法判断残留区域到底由哪道门禁造成，也无法量化停车时间改善。
